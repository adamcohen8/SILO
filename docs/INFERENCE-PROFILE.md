# First inference evaluation profile

The data-only [candidate profile](../profiles/nemotron-30b-4090-candidate.json) records exact source revisions and publisher metadata. It does not execute commands or select the production architecture. On 6 October 2026 the complete model and pinned Windows CUDA archives were downloaded and locally hash-verified. The [asset inventory](../profiles/nemotron-30b-4090-assets.json) and [GPU baseline](GPU-BASELINE-2026-10-06.md) record all 53 layers on the RTX 4090, short synthetic timings and a successful structured tool round trip. One requested line locator failed; full functional acceptance and deployment readiness remain false.

The starting experiment is Nemotron 3 Nano 30B-A3B with the Unsloth IQ4_XS GGUF (18,168,955,680 bytes, about 16.9 GiB) and a pinned llama.cpp CUDA source revision. This is a third-party quantization. Its size leaves more nominal room within 24 GiB than that repository's Q4_K_M asset (24,574,373,664 bytes, about 22.9 GiB); runtime buffers, context/state, display use, and other workloads still need measurement. This comparison is an inference from publisher sizes, not proof that IQ4_XS fits or that its quality is acceptable. See [publisher files](https://huggingface.co/unsloth/Nemotron-3-Nano-30B-A3B-GGUF/tree/9ad8b366c308f931b2a96b9306f0b41aef9cd405).

Use one concurrent request and an 8,192-token context. The earlier GPU baseline used a 1,024-token generation limit with reasoning disabled. The passing [contained document workflow](WINDOWS-AGENT-ISOLATION-2026-10-06.md) uses 2,048 generated tokens, reasoning enabled with a 512-token budget, the embedded Jinja template and native PEG parser. These are experiment settings, not model maxima or quality guarantees. The tool-call sampling settings follow [NVIDIA's model guidance](https://huggingface.co/nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B-BF16/tree/bf77c3174f68ad409e1c2aa60daeb46e32d1c606). Truncated/incomplete chat or tool output must fail.

Native Windows CUDA has now completed the synthetic graph/parser/GPU workflow in zero-capability AppContainer jobs over a private Windows AF_UNIX socket and document-tool pipes. Full isolation acceptance remains pending. A WSL alternative needs a separate tested profile and the same acceptance gates. No automatic CPU/cloud/runtime fallback is allowed. See [llama.cpp tool calling](https://github.com/ggml-org/llama.cpp/blob/50569eb87df530daff11afda229ceb9ab8e6cae8/docs/function-calling.md).

The local evaluation used llama.cpp release `b11433`, resolving to the existing pinned source commit. Both archives, all 55 extracted runtime files, the model payload and license source texts are now hash-recorded; the embedded template hash is in the local baseline evidence. Upstream and quantizer cards link separate NVIDIA licenses, both preserved for this local synthetic evaluation. Before distributing a complete bundle, resolve their notices/terms, pin every remaining Python wheel and platform dependency, and establish signed trust. Source commit IDs and publisher hashes alone provide no signature. The current Mac agent dependency file is not a Windows production lock.

Target measurements must record the profile/hash identities, Windows build, GPU driver, available/peak VRAM, load time, generation latency, completion/timeout/OOM behavior, and whether simultaneous host use works. Evaluate real structured tool calls through LangGraph, including unavailable folders, malicious document instructions, citations, stale sources, and reviewed new-copy saves. A small synthetic corpus cannot establish general accuracy or CUI authorization.
